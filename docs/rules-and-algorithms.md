# Rules and algorithms for web information extraction

## What the research establishes

The pipeline uses **both general and specific rules**, along with heuristic, statistical, and learned algorithms. A rule expresses a condition and an action. An algorithm specifies a procedure and can evaluate rules, rank candidates, cluster documents, or predict labels. Mozilla Readability, for example, is an algorithm built from hand-written DOM heuristics. A language detector can also be an algorithm with parameters learned from data. [Mozilla Readability implementation](https://github.com/mozilla/readability/blob/main/Readability.js) · [fastText language identification](https://fasttext.cc/docs/en/language-identification.html)

The main design question is which decisions can be made before choosing the goal. Standards and security controls apply across topics. Page quality and language heuristics also transfer across topics, with thresholds that can vary by page type and corpus. The goal determines which information is relevant, which relations or fields matter, and what evidence is sufficient to deliver a result.

| Scope | What it governs | When to define it |
| --- | --- | --- |
| General standards and invariants | HTTP semantics, robots matching, bounded fetches, safe destinations, immutable document versions, and evidence validation. | Before collecting or processing input. |
| General algorithms with tunable parameters | DOM scoring, near-duplicate detection, language identification, segmentation, and broad candidate generation. | Compare across representative inputs. Tune thresholds against labeled results. |
| Source or page-type rules | Site scope, API field mapping, allowed retention, selectors for a recurring layout, and content structure that needs preservation. | When configuring sources and after measuring where general methods fail. |
| Goal-specific rules and labels | Topical relevance, entity and relation types, required fields, sufficiency of evidence, and actions a downstream system can take. | Once a downstream question and expected output are defined. |

These scopes can combine. A general matcher can apply a site-specific selector or a goal-specific rule. A statistical classifier can serve several topics with the same broad labels, or it can be trained specifically for one task.

## Acquisition and document processing

| Stage | Methods to compare | What remains specific |
| --- | --- | --- |
| Discovery | RSS, Atom, APIs, and permitted datasets supply links or structured records. For HTML, parse links, resolve and normalize URLs conservatively, deduplicate the frontier, and use a bounded queue. Scrapy exposes link filters and request fingerprints as concrete references. | Allowed sites and paths, crawl depth, request budgets, feed or API mappings, and which links are worth following. [Scrapy link extractors](https://docs.scrapy.org/en/latest/topics/link-extractors.html) · [Scrapy request fingerprints](https://docs.scrapy.org/en/latest/topics/request-response.html#request-fingerprints) |
| Fetch eligibility | Apply HTTP and robots semantics, destination checks, rate limits, and response budgets deterministically. Use known access signals, such as Cloudflare's documented challenge header, to assign a disposition. | Source terms, permitted access routes, retry budgets, and retention rights. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) · [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html) · [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) · [Cloudflare challenge detection](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/) |
| Unusable pages and noise | Start with response checks and labeled signals for empty content, soft errors, consent pages, challenge pages, and likely JavaScript shells. Compare multi-signal heuristics or a lightweight classifier for ambiguous cases. DataTrove's repetition and document-quality filters are useful baselines for text quality. | Error templates and quality thresholds depend on page type. Corpus-cleaning thresholds require evaluation before adoption. Relevance needs a query or goal. [FineWeb experiments](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1) · [DataTrove filters](https://github.com/huggingface/datatrove/tree/main/src/datatrove/pipeline/filters) |
| Main content | Compare raw DOM text, semantic HTML and selectors, Readability's scoring and cleanup, and Trafilatura's extraction heuristics. A learned alternative such as Web2Text classifies text blocks using local and structural context. | Site-specific selectors can recover structured content missed by general extractors. Benchmark by page type and measure retention of evidence, tables, and other structure the chosen goal needs. [Readability](https://github.com/mozilla/readability) · [Trafilatura paper](https://aclanthology.org/2021.acl-demo.15/) · [Web2Text paper and code](https://github.com/dalab/web2text) · [Cross-extractor comparison](https://downloads.webis.de/publications/papers/bevendorff_2023c.pdf) |
| Language, segmentation, and duplicates | Use declared language as a signal and compare with a language detector when needed. Use Unicode segmentation as a baseline, exact hashes for identical representations, and MinHash over text shingles for near duplicates. Keep one observation per source and version even when documents cluster. | Short or mixed-language inputs, similarity thresholds, and the distinction between syndication and independent reporting require corpus checks. [Unicode segmentation](https://www.unicode.org/reports/tr29/) · [fastText language identification](https://fasttext.cc/docs/en/language-identification.html) · [DataTrove MinHash code](https://github.com/huggingface/datatrove/blob/main/src/datatrove/pipeline/dedup/minhash.py) |
| Search and relevance | BM25 ranks text against a query and works as a lexical baseline. Compare a classifier or semantic retrieval only where labeled examples show a gap. Use separate scores for relevance, source credibility, evidence support, and extraction confidence. | The query, acceptable recall and precision, and what counts as relevant depend on the user's decision or research question. [Tantivy](https://github.com/quickwit-oss/tantivy) · [fastText classification paper](https://aclanthology.org/E17-2068/) |

Run these comparisons on saved representations where possible. Acquisition and evidence checks can be evaluated across sources now. Relevance and preservation of question-specific evidence need a downstream task.

## Turning text into information

The [information extraction research](information-extraction-research.md) compares semantic extraction tasks, methods, evidence requirements, and benchmark design in more detail.

| Approach | What it produces | Where it fits and what to measure |
| --- | --- | --- |
| Structured fields | Values from feeds, APIs, and recognized markup with an explicit source location. | Start here when available. Test source-field mapping, missing values, and contradictions between metadata and visible text. [Schema.org Article](https://schema.org/Article) |
| Reusable linguistic components | Tokens, sentences, date and quantity candidates, entity mentions, quotation and attribution spans, and cues for polarity or modality. | These are candidate annotations. Resolving a date may need context, and finding a number alone leaves its role open. Evaluate span boundaries, binding to the correct subject or predicate, and uncertainty. [SUTime rules and examples](https://stanfordnlp.github.io/CoreNLP/sutime.html) · [PARC attribution corpus](https://aclanthology.org/L16-1619/) · [FactBank guidelines](https://catalog.ldc.upenn.edu/docs/LDC2009T23/annotationGuidelines.pdf) |
| Open information extraction | Candidate relations with predicates expressed in the text, without a fixed relation inventory. | Use for early discovery or as a broad baseline. ReVerb uses syntactic and lexical constraints. OLLIE studies contextual information such as attribution and conditions. Evaluate with CaRB for open triples and add checks for attribution, negation, and evidence. A downstream task can require normalization and additional fields. [ReVerb paper and implementation](https://reverb.cs.washington.edu/) · [OLLIE paper](https://aclanthology.org/D12-1048/) · [CaRB benchmark](https://aclanthology.org/D19-1651/) |
| Schema-based extraction | Filled fields for a defined claim, event, relationship, procedure, or decision. | Use when the required output is known. Begin with structured sources and bounded token patterns. Add typed dependency rules for cases where word order and attachment vary. Odin and Odinson show how to bind triggers to named arguments. Evaluate required roles and evidence spans, including cases where the correct result is unknown. [Odin paper](https://aclanthology.org/P15-4022/) · [Odinson code](https://github.com/lum-ai/odinson) · [spaCy pattern matchers](https://spacy.io/usage/rule-based-matching) · [NIST slot filling guidelines](https://tac.nist.gov/2012/KBP/task_guidelines/TAC_KBP_Assessment_Guidelines_V3.2.pdf) |
| Supervised and hybrid extraction | Candidate entities, relations, or spans predicted by a trained component and checked against rules or a schema. | Compare lightweight classifiers or taggers when repeated rule failures have enough annotated examples. Consider an LLM for a measured gap and score it on the same task, evidence contract, and test split. Track unsupported outputs, latency, and cost alongside recall. [fastText classification paper](https://aclanthology.org/E17-2068/) · [RECESS span extraction benchmark](https://aclanthology.org/2023.ijcnlp-main.6/) |

The papers and open-source implementations provide techniques to reproduce or benchmark. Adopt a runtime dependency only after an upstream maintenance, licensing, advisory, and compatibility check. Prefer established Rust components for the prototype. Reference implementations in other languages can run offline for comparison.

## Representing knowledge and deriving conclusions

- **Storage and search.** Keep raw snapshots where permitted, normalized documents, and extracted records linked by stable IDs. JSON Lines and relational storage can support inspection and replay. A graph is useful when requirements include cross-document relationships or multi-hop queries. Entity matching can start with exact identifiers and aliases, then use probabilistic record linkage if ambiguous matches matter. [W3C PROV](https://www.w3.org/TR/prov-dm/) · [Oxigraph](https://github.com/oxigraph/oxigraph) · [Splink record linkage](https://github.com/moj-analytical-services/splink/blob/master/docs/topic_guides/theory/fellegi_sunter.md)
- **Reasoning.** Symbolic rules can derive a result from typed facts and preserve its supporting inputs. The rule engine can be reusable. Predicates, assumptions, and permitted conclusions come from the goal. Soufflé's provenance mechanism is a reference for exposing derivations. [Soufflé provenance](https://souffle-lang.github.io/provenance)
- **Causality.** An extractor can capture a stated cause, effect, and supporting words. Estimating the effect of an intervention requires a causal question, data, and identification assumptions. Those requirements govern the choice of causal algorithm. [RECESS](https://aclanthology.org/2023.ijcnlp-main.6/) · [Pearl's causal calculus](https://proceedings.mlr.press/r0/pearl95a.html)
- **Decision and action support.** Identifying a decision or an instruction in a document is an extraction task. Recommending or taking an action also depends on the user's objective, constraints, authority, and tolerance for errors. Once the goal is defined, evaluate whether the extracted fields let a reviewer make the intended decision.

## Research sequence

1. **Evaluate the common pipeline.** Use permitted snapshots and synthetic failure fixtures across document types. Compare fetch dispositions, boilerplate removal, document and passage retention, duplicate clustering, and provenance. Measure false rejection so useful short or unusual pages stay visible.
2. **Compare general extraction methods.** Evaluate structured-field capture, linguistic annotations, and Open IE on their respective benchmarks. Report what each produces and where scope, attribution, ambiguity, or layout causes failures. Use these findings to inform which goals are feasible.
3. **Define the first downstream question.** Specify who uses the result, the decision or question it serves, the output fields, required evidence, and acceptable errors. Use those requirements to create gold labels before writing specific rules.
4. **Select the simplest method that meets those requirements.** Compare publisher fields, token patterns, dependency patterns, or a trained component on the same held-out documents. Evaluate candidates with field-level precision and recall, evidence support, and abstention. Add an algorithm or model when its contribution can be measured.

The proposed baseline is standards-based access checks, simple page heuristics, a measured boilerplate extractor, and versioned evidence. The semantics research should compare open extraction with schema-based extraction before committing to the product's first information goal.
