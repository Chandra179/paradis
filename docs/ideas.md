# Web Information Extraction Research and Evaluation Specification

## Research outcome

Given permitted English-language web sources, determine which methods reliably retrieve usable content and preserve enough evidence for a reviewer to verify later extraction. Each attempted input should have an inspectable disposition, and each retained document should have a traceable source version.

The downstream information goal remains open. The research should show what can be done with common standards and algorithms, which choices depend on a source or layout, and which decisions require a defined question and output schema. Compare approaches that work without generative AI first. Use the evidence to choose what the first semantic extraction experiment should optimize.

## Acquisition and content disposition

Try RSS, Atom, documented public APIs, and datasets with suitable usage rights before fetching article pages. A feed item may supply the evidence itself or serve as discovery if it only contains a summary. Record feed item IDs or API record IDs and pagination or cursor state as applicable. Record dataset version and source record locator. For missing coverage, try a direct HTTP GET of a permitted URL. Expand discovery from seeds to sitemaps and eligible HTML links only when measuring coverage that the structured channels miss. Every discovered URL goes through the same access checks as a seed. [RSS 2.0](https://www.rssboard.org/rss-specification) · [Atom RFC 4287](https://www.rfc-editor.org/rfc/rfc4287.html) · [Sitemaps protocol](https://www.sitemaps.org/protocol.html)

Maintain a source registry with allowed origins and paths, permitted acquisition modes, an identifiable crawler user agent, request limits, and terms or license references for collection, storage, and export. Public dataset access and downstream content-use rights are separate decisions. Record where each link came from. Resolve relative URLs with a standards-based parser, skip fragments for HTTP fetch identity, and retain query semantics unless a source-specific rule establishes equivalence. Cap crawl depth, queued URLs, redirects, and requests per origin. Revalidate each redirect before connecting and treat site-supplied canonical URLs as hints. [WHATWG URL Standard repository](https://github.com/whatwg/url) · [Common Crawl terms of use](https://commoncrawl.org/terms-of-use)

For web crawling, evaluate `robots.txt` for the origin and crawler identity before fetching content. Apply RFC 9309 matching and precedence, and cache the policy with an expiry and decision record. Under the RFC, an unavailable robots file such as a 404 may permit access, while an unreachable file due to a network or server error requires assuming complete disallow subject to the RFC's cache provisions. Pilot policy treats a 401, 403, or challenge on the robots request as restricted and a 429 as deferred. Check terms, access restrictions, and retention rights independently of the robots result. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)

| Signal | Disposition |
| --- | --- |
| Interim `1xx` | Wait for the final response. An upgrade is outside the supported content flow. |
| `200` or other eligible successful response | Check media type, encoded and decoded size, completeness, charset, and actual payload. |
| `204` or `205` | Record no content. |
| `206` | Record partial content unless completeness has been verified. Whole-document extraction requires a complete representation. |
| `301`, `302`, `303`, `307`, `308` | Resolve the location and apply access and destination checks at each hop. Record the redirect chain. |
| `304` | Reuse the corresponding cached representation and record the revalidation. On a cache miss, obtain a full response within policy. |
| `401`, `403`, `451`, login, paywall, or access challenge | Record the restriction and stop that route. A Cloudflare `cf-mitigated: challenge` response is a documented challenge signal. |
| `404`, `410`, or high-confidence soft 404 | Record missing or gone. Assess a soft 404 using the page content, even on HTTP 200. |
| `429` or retryable service failure | Back off per origin. Honor applicable `Retry-After` values and use bounded retries for transient failures. Record other HTTP failures by status. |
| DNS, TLS, timeout, broken connection, or truncated transfer | Record the transport or completeness failure independently of HTTP status. |

HTTP handling follows the protocol semantics. Content-level judgments such as soft 404 and likely JavaScript shell are classifications with recorded signals. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html) · [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html) · [Cloudflare challenge detection](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/) · [Google Search soft 404 documentation](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors#soft-404-errors)

Before article extraction, distinguish empty bytes, whitespace, missing meaningful HTML body, unsupported type, soft errors, consent-only pages, parked or advertising-only pages, and likely JavaScript shells. After extraction, record empty or incomplete main text, language, page type, topic relevance, and duplication. Retain separate signals and a disposition such as accepted, skipped, restricted, deferred, or uncertain. Use link density, repeated blocks, visible text, and known error text as signals. Evaluate them by page type. Useful information can appear alongside ads, and a short notice can be the entire relevant document. [FineWeb filtering experiments](https://huggingface.co/spaces/HuggingFaceFW/blogpost-fineweb-v1) · [DataTrove](https://github.com/huggingface/datatrove)

Evaluate browser rendering later if the HTTP experiment finds a material gap on **permitted JavaScript-dependent** pages. Use a bounded wait for a documented content signal and classify the rendered result again. Access blocks stay terminal for that route. For blocked sources, use a publisher-provided channel with appropriate rights or obtain permission from the source. Compare a Rust client such as Chromiumoxide or Fantoccini with first-party Playwright controlling Chromium. Playwright lists JavaScript/TypeScript, Python, Java, and .NET as supported languages. Playwright MCP fits a later supervised source-exploration experiment. Cloudflare does not support browser automation frameworks for solving production challenges. [Chromiumoxide](https://github.com/mattsse/chromiumoxide) · [Fantoccini](https://github.com/jonhoo/fantoccini) · [Playwright supported languages](https://playwright.dev/docs/languages) · [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp) · [Cloudflare supported browsers](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)

## Main content extraction

Collect publisher metadata from feed or API fields, HTML metadata, and recognized Schema.org JSON-LD. Record the origin of each field and preserve disagreements, for example when a feed date and a page date differ. Keep publication, modification, retrieval, and event dates distinct. Parse known JSON-LD fields locally with external context resolution disabled. [Schema.org NewsArticle](https://schema.org/NewsArticle)

Compare raw DOM text, a semantic element or CSS-selector baseline, upstream Mozilla Readability with a local DOM, and Trafilatura or Resiliparse on the same saved HTML. Use one Rust Readability candidate in the comparison if it meets the dependency gate. Preserve headings, block order, bylines, tables, captions, or quotations when the task needs their context. Measure both main-text quality and whether the supporting passages for the target fields survive cleaning. Use the simple selectors as an estimate of what source-specific maintenance would buy. [Mozilla Readability](https://github.com/mozilla/readability) · [Trafilatura](https://aclanthology.org/2021.acl-demo.15/) · [Resiliparse](https://github.com/chatnoir-eu/chatnoir-resiliparse) · [Bevendorff et al. comparison](https://downloads.webis.de/publications/papers/bevendorff_2023c.pdf)

## Extraction rules and knowledge representation

The [rules and algorithms research](rules-and-algorithms.md) compares general and goal-specific methods across the pipeline. The [information extraction research](information-extraction-research.md) goes deeper on semantic tasks, published methods, and how to benchmark them.

Start with source-provided structured fields and reusable text annotations. Compare open information extraction for broad relation candidates and schema-based extraction once required fields are known. Choose rule patterns, classifiers, or model-assisted extraction based on their performance on the same evidence and evaluation set.

Start with versioned documents and evidence-linked records so results can be inspected and replayed. Add graph queries or symbolic derivations when a defined goal calls for them. Keep attributed causal statements traceable to their source. Causal inference requires a separate question, appropriate data, and identification assumptions.

## Source quality and information quality

| Dimension | What to record or evaluate |
| --- | --- |
| Source credibility | Publisher and speaker identity, whether each was in a position to know, and whether reporting is primary, independent, or syndicated. |
| Document quality | Completeness, language, detected page type, boilerplate, publication or update time, and relevance to the monitored topic. |
| Claim support | Whether the selected text supports the subject, statement, attribution, tense, polarity, and values. |
| Claim credibility | Evidence strength, freshness relative to the question, independent corroboration, and conflicting or superseding statements. Unknown is a valid state. |
| Extraction reliability | Rule and version, known limits, and measured precision and recall for that rule or field on labeled examples. |

A credible source can still publish a stale statement. An ad-supported article can contain primary evidence. Fifty copies of one press release count as one upstream attestation when evaluating corroboration. Use exact hashes to detect repeated bytes or normalized text, and add near-duplicate clustering when syndicated copies affect evaluation. Preserve the source-level observations and keep both sides of genuine conflicts. A rule's reliability measures agreement with the document and annotation, while claim credibility depends on the evidence beyond that match. [DataTrove deduplication](https://github.com/huggingface/datatrove) · [W3C Data Quality Vocabulary](https://www.w3.org/TR/vocab-dqv/)

## Provenance and retention

Keep three linked records. JSON Lines is the proposed portable interchange format for independent replay and scoring. The retention policy controls which byte or text snapshots can be stored, for how long, and what may be exported.

| Record | Minimum information |
| --- | --- |
| Acquisition attempt | Source ID, discovery record or parent URL, requested and final URL where applicable, redirects, UTC retrieval time, acquisition mode, status or error, access-policy decision and version, and disposition. Record payload digest and safe validators when available and permitted. |
| Document version | Stable source and version IDs, permitted raw snapshot or immutable upstream locator, hash of the bytes actually supplied to parsing when permitted, publication and modification values plus their origin, parser and extractor versions, normalized text and hash where retained, and link to an earlier or superseding version when known. A changed representation gets a new version. |
| Claim | Document version ID, schema and extraction versions, method, rule or model ID where applicable, typed fields, and evidence spans for supported fields. Derived relations additionally retain their inputs and derivation rule. |

Use half-open UTF-8 byte offsets in a named normalized-text version. Verify that each span lands on character boundaries and matches its quote. Keep contextual text where needed to establish scope and attribution. Link the normalized document to the original snapshot or equivalent versioned upstream record. Keep a source locator, such as a DOM block or JSON pointer, where the source provides one. A hash can validate matching bytes. The evidence itself must remain inspectable under the source policy for a result to count toward the pilot. If raw retention is restricted but the normalized text or snapshot locator is permitted, record that mode and confirm the exact version can be inspected. Where the policy allows only metadata, record the attempt and exclude unverifiable claims from delivered results. Redact sensitive URL parameters and headers from logs and public artifacts. [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) · [W3C Web Annotation selectors](https://www.w3.org/TR/annotation-model/#selectors) · [Common Crawl archive formats](https://commoncrawl.org/get-started)

## Security requirements

- **Network boundary.** Use configured origins and HTTP(S) only. Validate scheme, authority, and resolved IPv4 and IPv6 destinations, and enforce policy on the address actually connected to. Block non-public, internal, and infrastructure metadata destinations. Apply controls to retries, robots redirects, sitemaps, feeds, every redirect, and later browser subrequests. Disable automatic redirects unless the client can enforce each hop. Use scoped credentials only for configured APIs and keep them within their designated origin. [OWASP SSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
- **Resource limits.** Cap time, in-flight requests, wire bytes, decompressed bytes, and parsing work. For XML, disable external entity processing and bound nesting and expansion. For offline datasets, apply the same decompression and parsing budgets. Record incomplete input and stop processing it. [OWASP XML external entity prevention](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html)
- **Content and storage boundary.** Treat external HTML, XML, links, metadata, and extracted strings as untrusted. Prefer escaped plain text to display evidence. Sanitize any preview HTML, keep raw artifacts inert and access-controlled, and avoid logging bodies, credentials, or private data. Readability is a content extractor and requires separate sanitization when its HTML is displayed. [Mozilla Readability security guidance](https://github.com/mozilla/readability#security)
- **Browser and model boundary.** If browser rendering is evaluated, use isolated, disposable contexts behind enforced egress controls, without personal sessions or access to host secrets. Use a supervised, read-only tool configuration for any later MCP or model experiment. Treat page text and tool responses as data. Require structured model output, validate all evidence references independently, and keep access and tool permissions outside model control. [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp) · [OWASP prompt injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)

## Evaluation and delivery gates

Assemble a varied set of permitted or synthetic inputs for the common pipeline. Include articles, documentation, feed-only and API cases, near duplicates, corrected versions, non-English text, noise, restricted and empty responses, and permitted JavaScript shells. Split by publisher domain and duplicate cluster before tuning. Freeze fixtures and config for replay. After choosing a semantic goal, label target fields and their supporting passages along with near misses and ambiguous cases. Use a small double-labeled subset to settle disagreements before scaling annotation. Use the article benchmark or WCEB for extractor comparisons and the causal and Open IE corpora for supplemental tests subject to their applicable terms. [ScrapingHub article benchmark](https://github.com/scrapinghub/article-extraction-benchmark) · [WCEB evaluation](https://downloads.webis.de/publications/papers/bevendorff_2023c.pdf)

The numeric targets below are proposed pilot gates. Each check is unverified until run on the frozen fixtures or an approved live sample. Report denominators, recall and precision by field and source type, and uncertainty when sample sizes are small. Record how many target claims were lost at each stage so downstream precision can be interpreted alongside end-to-end recall.

| ID and type | Requirement | Fitness function |
| --- | --- | --- |
| O1 · Outcome | A reviewer can answer the chosen question and inspect the evidence. | After defining the question and output schema, set field-level acceptance criteria and blind-review sampled results against annotated documents. Score exact field attachment, evidence support, and appropriate abstention. |
| O2 · Outcome | Each input has an explainable disposition, and eligible documents reach extraction. | Compare with transport and page fixtures plus a permitted live sample. Aim for at least 95% useful-document retention and 95% precision on invalid-page decisions. Report retrieval success only over eligible targets, with category counts for all attempts. |
| O3 · Outcome | Main text retains useful content for each supported page type. | Compare raw DOM, selectors, Mozilla Readability, and a suitable Rust candidate on the same HTML. Report main-text precision and recall by page type, with latency and memory. Measure retention of annotated supporting passages once the downstream goal defines them. |
| I1 · Invariant | Every delivered claim has inspectable, versioned evidence and reproducible extraction metadata. | Require 100% pass on resolvable version, hash where applicable, byte slice, quote, and rule-version checks. Compare ordered semantic output from repeated runs over the same snapshots and config. Review whether evidence actually supports each sampled field. |
| I2 · Invariant | Information quality and source identity survive syndication, contradictions, and corrections. | Check a copied article cluster, two independent disagreements, and a publisher correction. Verify provenance remains available and corroboration counts respect source independence. |
| C1 · Constraint | Every request conforms to source policy and the network boundary. | Use controlled fixtures and a mock resolver for disallow, robots failure, access challenge, throttling, redirects, and DNS changes. Require zero forbidden connections and zero fetch escalation for restricted inputs. |
| C2 · Constraint | Untrusted content stays within resource, rendering, and retention boundaries. | Exercise oversized and compressed fixtures, inert markup, expired retention, and metadata-only permissions. Require limits to stop work and prevent prohibited retention or display. |
| C3 · Constraint | First extraction pass works without generative AI and uses Rust with eligible dependencies. | Run the frozen extraction fixtures offline, build on the pinned toolchain, run the dependency checks, and record which non-Rust tools served solely as offline comparators. |

Begin with saved representations across several page types. Compare structured acquisition and direct HTTP where the same content is available, and measure content cleaning independently. Review false rejections and important text dropped during cleaning. Measure the coverage gap before expanding discovery or testing browser rendering. Use the semantic research to choose a downstream question, then evaluate extraction methods against its required fields and evidence. Let those results guide the architecture.
